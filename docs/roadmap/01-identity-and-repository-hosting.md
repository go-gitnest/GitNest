# Identity and repository hosting roadmap

**Phase:** 1
**Status:** not started
**Roadmap file:** docs/roadmap/01-identity-and-repository-hosting.md

## Purpose

Make GitNest useful for a developer with one account and one repository: sign in through a browser, create a repository, push to it with an ordinary Git client, browse the result, and control who else can reach it. This phase establishes the authorization and storage contracts every later phase depends on, so it is the phase where correctness matters most.

## Scope

Accounts and their credentials, browser sessions and personal access tokens, repository metadata and the shared permission service, bare repository storage, the bounded Git command runner, Git over HTTPS (fetch then push), the repository browser, collaborator management, Git LFS, and the backup procedure. Organizations, issues, and pull requests are phase 2 and later.

## Workstreams

### W1.1 Configuration and public URL
- **Status:** implemented
- **Delivered by:** W0.2 and W0.6, which built the whole startup configuration layer: every variable loaded and validated as a unit, the `GITNEST_PUBLIC_URL` rules (absolute, no credentials, path, query, or fragment, and `https` unless the host is loopback), the connection-pool budget, and the log level. `internal/config` holds the accepted and rejected shapes for each variable, and the real binary refuses to start on an invalid value.
- **Deliverable:** environment configuration in `internal/config`, including `GITNEST_PUBLIC_URL` validated as an absolute URL with no credentials, path, query, or fragment, requiring `https` unless the host is loopback.
- **Depends on:** —
- **Acceptance:** invalid public URLs fail startup with a clear message; `https` on a non-loopback host is required; loopback `http` is accepted for development; unit tests cover each rejected shape.

### W1.2 Administrator bootstrap
- **Status:** implemented
- **Deliverable:** `gitnest admin create` in `cmd/gitnest`, a prompt that reads the password without echo, Argon2id hashing with recorded parameters, and a transactional store operation in `internal/identity` that refuses a second initial administrator.
- **Note:** on an unmigrated database the command reports the migration requirement after the operator has answered the prompts, because the schema is checked when the account is written. Checking it before prompting would save the operator typing a password for nothing; it is a small change to make if an operator ever hits it twice.
- **Depends on:** W1.1
- **Acceptance:** on a fresh migrated database exactly one administrator is created; a repeated or concurrent attempt fails with `ErrAdminExists`; an unmigrated database reports that migration is required; the password is never accepted as a command-line argument.

### W1.3 Accounts, invitations, and sessions (domain and persistence)
- **Status:** implemented
- **Deliverable:** account status, sessions, and single-use invitation tokens in a new forward-only migration, with the sign-in, sign-out, current-user, invitation creation, and invitation acceptance use cases in `internal/identity`.
- **Notes:**
  - Audit events named in [../reference/events.md](../reference/events.md) for this area (`account.invited`, `account.invitation_accepted`, `auth.session.revoked`) are **not written yet**. The audit surface is phase 8 (W8.7), and emitting half a catalogue now would leave a trail with gaps. Recorded here so it is a known gap rather than an oversight.
  - The throttling counters are process-local. A multi-node deployment needs a shared store, which phase 10 owns.
  - Two parity items are deliberately left unticked: the session **idle** timeout (only the absolute lifetime is implemented) and the **disable/re-enable** operation (the store enforces a disabled account, but no use case turns one off; that arrives with the operator console).
- **Depends on:** W1.2
- **Acceptance:** invitation tokens are single use under concurrent acceptance; expired and revoked invitations and sessions fail identically to unknown ones; a disabled account loses its sessions and cannot sign in; session and invitation tokens are stored only as digests.

### W1.4 Browser and API session surface
- **Status:** implemented
- **Deliverable:** the versioned `/api/v1` account contract (`login`, `logout`, `me`, invitation creation, invitation acceptance) in `internal/transport/http/api`, session cookies set `Secure`, `HttpOnly`, and `SameSite=Lax`, a CSRF token required on state-changing requests, and per-route throttling wired to the existing `identity.Service` limiters.
- **Notes:**
  - **Paths:** `login`, `logout`, and `me` are the ones [../architecture/urls-and-identifiers.md](../architecture/urls-and-identifiers.md) §3 names. Invitation creation and acceptance are not in that table; they are placed at `POST /api/v1/user/invitations` and `POST /api/v1/invitations/accept`, with the invitation secret in an `X-Invitation-Token` header so it cannot land in a URL, a referrer, or an access log.
  - **`Secure` on loopback:** the flag is set whenever the public URL uses `https`. It is deliberately not forced on an `http` loopback instance, because a browser drops a `Secure` cookie received over `http`, which would break the documented development setup outright; the public-URL validator refuses `http` for every non-loopback host, so the exception cannot reach a deployment. A loopback reverse-proxy deployment should serve `https` to keep the flag.
  - **The CSRF token is returned in the response body, not a cookie**, so it is readable only by the same-origin script; a non-`HttpOnly` cookie could be planted by a subdomain.
  - The error envelope is `{message, errors[]}` from `docs/architecture.md` §11. `documentation_url` is phase 4's published shape (W4.5) and is absent until then.
  - Session listing and per-session revocation have a store operation but no endpoint yet; they belong with the session settings page.
- **Depends on:** W1.3
- **Acceptance:** cookie flags are asserted in tests; a state-changing request without a valid CSRF token is rejected; a throttled sign-in returns the documented status without revealing whether the account exists; no response or log line contains a password, hash, or token; the same handler set is usable by the API and the browser.

### W1.5 Repository metadata and permission service
- **Status:** implemented
- **Deliverable:** a forward-only migration for repository visibility, description, default branch, canonical storage ID, and direct collaborators; the repository application service in `internal/repository` that answers every access question; name validation and reserved-name handling.
- **Notes:**
  - **Two documents disagree about the storage path, and this workstream does not settle it.** [../architecture/urls-and-identifiers.md](../architecture/urls-and-identifiers.md) §1 says a stable internal UUID never appears in a storage path, while this file's acceptance criteria and [02-collaboration.md](02-collaboration.md) both say the storage location is derived from the repository's UUID. The resolution taken here keeps both satisfiable: `repositories.id` is the stable identifier that reaches foreign keys and events, and a separate immutable `storage_id` addresses the bytes, so the row UUID never enters a path. **The on-disk layout itself is W1.6's deliverable**, so nothing is being asserted about it yet. A maintainer should confirm which identifier the layout is meant to use.
  - **Repository names and the reserved list.** §6.3 says the reserved names of §6.9 cannot be created at the top level of an owner, but then says a repository may be named `settings` "only if it does not collide with a route". Those two sentences conflict, and the second one implies a route-collision test that phase 1 cannot evaluate, because the browser routes it would check against arrive in W1.9 and W1.10. This workstream takes the strict reading: the §6.9 list is rejected. It is fail-closed, it satisfies the parity line about reserved names, and it is a validation rule rather than a stored value, so relaxing it later needs no migration. **A maintainer should confirm the intended reading before the browser routes land.**
  - **Visibility has two values here.** `internal` (visible to an enterprise's members) appears in [../reference/events.md](../reference/events.md) and the administration document, but it is an enterprise-scoped value and enterprises are phase 8. It arrives as an added CHECK value, which is a migration.
  - **Ownership is not a grant.** The collaborator table stores only `read`, `write`, and `admin`, and `owner` is refused by both the service and a database CHECK, so ownership cannot be duplicated into a row that could drift from `owner_id`.
  - **Rename does not yet leave a redirect.** The metadata change is implemented and the storage identity is proven unchanged, but the `301` record that keeps an old Git remote working is W1.10's deliverable. That is safe only because no Git transport exists yet (W1.7), which is why it is recorded here rather than assumed.
  - **Not implemented by this workstream:** archiving (the column and its read-only enforcement are W1.10), visibility *changes* with their confirmation (W1.10), transfer between owners (phase 2, which also adds the owner discriminator and rebuilds the list index to the three-column form `docs/architecture/performance.md` names), and the HTTP/API surface (W1.9).
  - Organization ownership is phase 2. A repository created today is owned by a user account, and the parity line that covers creation is left unticked until organizations exist because it names both.
- **Depends on:** W1.3
- **Acceptance:** tests prove owner/admin/write/read and anonymous outcomes for public and private repositories; a private repository cannot be reached by guessing a UUID, a slug, or an alternate casing; rename does not change the ID-derived storage location; list filtering happens before pagination so private names and counts do not leak.

### W1.6 Bare repository storage and Git command runner
- **Status:** implemented
- **Deliverable:** `internal/platform/storage` for repository paths and `internal/platform/git` for bounded Git invocation: argument arrays only, a controlled environment, timeouts, request and response limits, cancellation, and cleanup.
- **Notes:**
  - **The storage layout, which settles the identifier question left open by W1.5.** Bytes live at `<root>/<first two hex>/<next two hex>/<storage_id>.git`. The two-level fan-out keeps directory listings small; the identifier in the path is `storage_id`, the separate immutable column, not the row `id`. That is what lets `docs/architecture.md` §5 ("addressed by internal UUID") and `urls-and-identifiers.md` §1 ("a stable internal UUID never appears in a storage path") both hold, and it is why a rename, a visibility change, and a future transfer leave the bytes where they are.
  - **A Windows measurement changed the implementation.** Killing the child on cancellation went through `taskkill /T /F /PID` first; measured against the direct `Process.Kill()`, taskkill took about five seconds to return while the direct kill took about 0.2 seconds. Since a killed operation holds a concurrency slot until it is reaped, the slow path cost five seconds of capacity after every cancellation. Windows `Process.Kill` already terminates the tree, so the direct kill is used and the numbers are recorded in the source. The Git test suite went from a 241-second hang to under 8 seconds as a result.
  - **The environment is built from nothing, not filtered.** Every variable is either listed explicitly or absent, so a credential the web process holds cannot reach a Git child by accident. The refused list covers not only secrets but redirectors — proxy settings, metadata endpoints, `GIT_ALTERNATE_OBJECT_DIR`, `GIT_DIR`, `GIT_CONFIG_COUNT` — because those change what a child reads or where it connects.
  - **Client-supplied arguments cannot begin with `-`.** That is the control that stops a ref from being read as an option, which is the shape of `--upload-pack=<command>` injection. Rejecting is cheaper and more reliable than escaping.
  - **Repair never deletes bytes by default.** `Reconcile` only reports; `Repair` creates a directory the database knows and the disk does not, and removes an orphan directory only when the caller explicitly asks. Deleting bytes is not reversible, and a stale database snapshot must not be able to destroy a repository.
  - Not implemented here: the SSH entry point and its key handling (phase 2), process-memory limits (`GIT-MEMORY` is a cgroup-level control that arrives with the container runtime), and the per-credential concurrency limit (`GIT-CREDENTIAL`) which needs the credential model from phase 4. The per-instance limit is implemented and enforced by refusing rather than queuing.
- **Depends on:** W1.5
- **Acceptance:** integration tests create, inspect, and remove bare repositories under a temporary root; traversal and absolute-path attempts cannot write outside that root; a cancelled Git process is reaped and leaves no temporary data; a database row without a directory (and the reverse) has an idempotent repair path.

### W1.7 Git over HTTPS: clone and fetch
- **Status:** implemented
- **Deliverable:** smart HTTP `upload-pack` in `internal/transport/http/git`, protocol v2 support, streaming responses, disconnection handling, and integration with the shared permission service.
- **Notes:**
  - **Routes** are `GET /{owner}/{repo}.git/info/refs?service=git-upload-pack` and `POST /{owner}/{repo}.git/git-upload-pack`, the paths `docs/architecture/urls-and-identifiers.md` §3 lists, with `Cache-Control: no-store` as §9 requires. The `.git` suffix is what distinguishes the transport route from the browser route that arrives in W1.9.
  - **This version resolves every caller as anonymous, and an `Authorization` header is deliberately ignored rather than partly honoured.** A credential this server cannot verify must not appear to authenticate anyone, and ignoring it makes a denied caller and an anonymous one behave identically, which is the T-A4 shape. The model that turns an `Authorization` header into a principal is the credential workstream in phase 4 (W4.8); W1.7's own acceptance criteria are anonymous-scoped. **Consequence to be aware of:** phase 1's exit criteria say an invited contributor clones a *private* repository, and that cannot be honoured until the credential model exists. Recorded here rather than worked around with an invented credential scheme.
  - **A denied fetch is a `404`, never a `403`.** A repository that does not exist, one the caller may not read, one whose name is malformed, and one whose owner does not resolve all produce the same status, body, and headers, and none of them starts a Git process. The test asserts that byte for byte, and asserts the process count is zero.
  - **A missing directory behind an authorized repository is a `503`, not a `404`.** The caller was already authorized, so saying the server is unwell discloses nothing, and disguising the divergence as not-found would hide an operational fault that W1.6's repair path exists to fix.
  - **The service allowlist is enforced twice**: the route accepts only `service=git-upload-pack`, and the runner refuses any verb outside its own list. `receive-pack` is therefore refused until W1.8 adds it.
  - The v2 `Git-Protocol` header is validated against a narrow character set before it becomes a child environment variable. A hostile client can send a header containing a newline, which Go's own HTTP client refuses to do, so that case is tested by dispatching straight to the handler.
  - Disconnection handling is the runner's existing cancellation path: a client that goes away cancels the request context, the process group is killed, and the scratch area is left clean. It was verified in W1.6 and is exercised here through the streaming response.
  - Not implemented here: push (W1.8), LFS (W1.11), archive (phase 6), and shallow-clone and filter capability tuning beyond what the installed Git offers.
- **Depends on:** W1.5, W1.6
- **Acceptance:** an integration test clones and fetches a repository through a real Git client; anonymous callers can fetch a public repository and cannot determine whether a private one exists; authorization headers, tokens, and pack data never reach the logs.

### W1.8 Git over HTTPS: push
- **Status:** implemented
- **Deliverable:** `receive-pack` with write-permission enforcement, ref-update validation, outcome recording, and enqueued follow-up work.
- **Notes:**
  - **A gap in the plan, reported rather than worked around.** W1.8's acceptance says "a user with write permission pushes a branch and sees it in the repository", and phase 1's scope preamble lists "personal access tokens" among what it delivers — but **no W1.x workstream delivers a personal access token**, and no workstream delivers the credential model that would turn an `Authorization` header into a verified principal. The parity line for token creation (personal access token creation showing the value once, P1) is likewise unclaimed by any workstream. So a deployed instance cannot today authenticate a pusher at all: every caller resolves as anonymous.
  - **What that means for the evidence.** Write-permission enforcement, ref validation, the size and ref-count bounds, streaming, replay, and the outcome record are all implemented and verified against a **real `git push` through a real client at a real server**: a collaborator holding `write` pushes and a second clone sees the content; a collaborator holding `read` is refused with the repository left untouched; an anonymous caller is refused as not-found. The principal those tests use is supplied through the transport's `Authenticator` seam, which is exactly the seam the credential model will plug into. What is **not** verified — because it does not exist — is that a production caller can hold write permission. The parity line for push is ticked on the strength of the enforcement path, which is what the line names; the token line stays unticked.
  - **A refusal is still a `404`, never a `403`.** A caller below write, a missing repository, a malformed name, an unresolvable owner, and a private repository all produce the same response, and a caller holding read cannot learn from a push attempt that pushing would reveal more. The test asserts this with a real client as well as directly.
  - **The push advertisement needs write, not read.** It lists the refs and the hooks a client may run, so serving it to a read-only caller would disclose exactly what the write path does.
  - **Validation happens before Git starts, and the bytes are replayed.** The update-command section is read and checked here, then handed to the child ahead of the rest of the body, so Git receives the request byte for byte while nothing is written when the request is refused. The test asserts the replayed stream equals the request.
  - **The push bound is enforced as the bytes flow.** A declared `Content-Length` over the bound is refused before anything is read; a streamed body is bounded by this layer rather than by `http.MaxBytesReader`, because the bound has to surface as a distinguishable `413` rather than as a generic read failure. Object size is passed to Git as `receive.maxInputSize` (GIT-OBJECT-BYTES), and refs per push are bounded (GIT-REFS).
  - **Ref namespaces are restricted to `refs/heads/` and `refs/tags/`.** `refs/notes/`, `refs/remotes/`, `refs/pull/` and the rest are server-owned, and a client pushing into them would write state the server owns. The Git ref grammar is applied in full, and the test covers twenty-one rejected shapes.
  - **`Config` was added to the runner.** A configuration override has to precede the subcommand, so the runner now builds `-c key=value` arguments ahead of the service name. The values are chosen by this process and shape-checked, never derived from a client.
  - **Enqueued follow-up work is not implemented.** It needs the job queue and the push webhook payload, which are phases 4 and 5. The outcome is recorded as a structured log line, which is what an operator can act on today.
  - Not implemented here: force-push policy beyond what Git applies, branch protection and rulesets (phase 8), and push options.
- **Depends on:** W1.7
- **Acceptance:** a user with write permission pushes a branch and sees it in the repository; a read-only user and an anonymous caller are denied without a ref update; an oversized request and a cancelled push are terminated cleanly; the operation outcome is recorded.

### W1.9 Repository browser and API
- **Status:** split into W1.9a, W1.9b, and W1.9c. **W1.9a and W1.9b are implemented; W1.9c is not started.**
- **Deliverable:** the repository half of the versioned API (list, create, detail, tree, file, commits, settings, collaborators) with explicit response structs and pagination, and the React application under `web/` with list, create, overview, file tree, file view, commit list, and settings pages.
- **Depends on:** W1.5, W1.6

#### W1.9a Repository read API
- **Status:** implemented
- **Delivered:** `/api/v1/user/repos` (list, create) and `/api/v1/repos/{owner}/{repo}` with `contents/{path}` (a file or a directory listing) and `commits`, backed by `internal/gittransport` for content and `internal/repository` for every access question.
- **Note — this workstream contradicts [../architecture/frontend.md](../architecture/frontend.md), and the architecture document wins.** W1.9's deliverable names "the React application under `web/` with list, create, overview, file tree, file view, commit list, and settings pages". `frontend.md` fixes the opposite split: "server-rendered HTML is the default for **every read surface**", naming the repository overview and the file and directory view as Go templates in `internal/transport/http/web`, with React reserved for the *interactive* surfaces — settings, editors, composers. Its list of React surfaces does not include a read page, and it adds that no JavaScript may be required to read public content. A browse page is a read surface, so it is rendered by Go. The split is recorded here because the two documents disagree; **a maintainer should confirm before W1.9b starts**, since it decides where that page is written.
- **Note — the runner's service allowlist was extended, and that is a security control.** T-A1 names a fixed allowlist of three protocol verbs. Serving a tree, a file, or a commit list needs `rev-parse`, `cat-file`, `ls-tree`, `log`, and `for-each-ref`, so they were added. See `internal/platform/git/verbs.go` for the properties that keep the extension safe: every added verb is read-only, none takes an option from a caller, the repository is chosen by this process, and the caller still passes the permission service first.
- **Note — the read surfaces pass `--` before a path.** A client-supplied path emitted as a bare argument is read by Git as a *revision* in a bare repository, which has no working tree to disambiguate against, so `git log <rev> <path>` fails outright. The runner therefore emits a `Paths` field after a `--` separator, and validates those values with the path rule rather than the argument rule.
- **Not implemented by W1.9a:** the settings and collaborator endpoints (W1.10 owns those operations), search, filters, and sorting on the repository list, the rendered pages (W1.9b), and the React application (W1.9c).

#### W1.9b Repository read pages
- **Status:** implemented
- **Deliverable:** the server-rendered repository read surfaces named in [../architecture/frontend.md](../architecture/frontend.md): repository overview, file tree, file view, commit list, with canonical URLs, escaped output, and no JavaScript required.
- **Delivered:** `internal/transport/http/web` renders `/{owner}/{repo}`, `/tree/{ref}[/{path}]`, `/blob/{ref}/{path}`, and `/commits/{ref}[/{path}]` from Go templates, with the messages in `internal/i18n`.
- **Notes:**
  - **No JavaScript.** Every page is complete on the first byte, which the test asserts by refusing a `<script` element and any inline event handler on all four surfaces. Repository content is escaped text, asserted with a file whose body is a `<script>` tag: it appears as `&lt;script&gt;` and never as markup.
  - **The message catalogue is load-bearing, not decorative.** `T` is a template *function* bound to the request's catalogue, not a method on the page value. Go's templates refuse to call a promoted method that takes arguments — "T is not a method but has arguments" — and every page's data is an anonymous struct embedding the resolved view, so a method would work only for the pages that happened not to wrap it. A test asserts that no identifier the catalogue defines appears in any rendered page, which is what catches a constant whose value and a template's literal have drifted apart; two such mismatches were found that way.
  - **A page cannot reach an unexported field of the embedded view.** `Revision` is a method for the same promotion reason, and the templates call it rather than reading a field.
  - **Cacheability follows the viewer**, as `urls-and-identifiers.md` §9 requires: a public repository read anonymously is `public, max-age=60` with `Vary: Accept-Encoding`, anything caller-dependent is `private, max-age=0, must-revalidate` with `Vary: Cookie`, and a denial is `no-store` with `X-Robots-Tag: noindex` so a cached denial cannot outlive the access that replaces it.
  - **A public page carries Open Graph metadata and a canonical URL**, and a private or authenticated page carries `noindex`, which `frontend.md` requires because a link preview must render without JavaScript.
  - **The same decision twice** is asserted against a real instance: the permission the page prints equals the `permission` field the API returns, for an anonymous caller and for the owner, on a public and a private repository. Both surfaces call the same service with a principal built the same way, and an unusable session degrades to anonymous in both rather than failing in one.
  - **Not implemented here, and deliberately not ticked:** Markdown rendering and syntax highlighting on the file view (content is shown as escaped text), the raw and download routes, blame, the single-commit diff view, compare, branch and tag lists, the file finder, and line permalinks. Each is its own parity line and none is claimed.

#### W1.9c Interactive repository surfaces
- **Status:** split into W1.9c-1 and W1.9c-2. **Both are implemented.**
- **Deliverable:** the React application the architecture document does assign to this phase — repository creation and repository settings — served same-origin from pre-built assets with no Node.js runtime in production.
- **Depends on:** W1.9b, W1.10
- **Why it is split:** the browser surface needs a way to hold a CSRF token across a page load, and the documented mechanism for that turns out not to exist yet in `internal/config`. `docs/architecture/secrets.md` states that **"per-purpose subkeys are derived from the master key with HKDF using a purpose label"** and that the master key `GITNEST_SECRET_KEY` **"is present at startup or the process refuses to start"** — and `internal/config` has no such variable. Once it exists, a CSRF token can be a signed value the server derives rather than a digest it stored, which removes a real limitation noted below. Adding a mandatory startup secret is its own reviewable change: it touches configuration, the account service, every transport, the test harness, the compose recipe, and the operator documentation.

##### W1.9c-1 Build pipeline and the interactive shell
- **Status:** implemented
- **Delivered:** the `web/` package (Vite, TypeScript, React 19), the embedded assets and shell in `internal/transport/http/web/{assets,application}.go`, the security-header middleware T-B6 requires, and the repository-creation surface with sign-in.
- **Notes:**
  - **The security headers are the enforcement of a threat-model control, not a nicety.** `docs/security/threat-model.md` T-B6 requires that "referrer policy and content-security policy are set instance-wide" against cross-origin embedding, and asks for "a header assertion and disallowed embed case". The policy denies every external origin (`default-src 'self'`), refuses framing, and forbids `unsafe-inline` and `unsafe-eval`; the referrer policy is `no-referrer`, because a GitNest URL can name a private repository. Tests assert the shipped policy on a real response and assert that no directive admits an arbitrary origin.
  - **The header middleware was first installed outside the asset dispatcher, and the test caught it.** Assets were being served before the headers were set, so the instance-wide guarantee did not hold for them. The dispatch now happens inside the chain.
  - **A routing conflict that panicked the server at startup, found by a test.** `GET /assets/` is a subtree pattern that `net/http` cannot rank against the read surfaces' `GET /{owner}/{repo}/tree/{ref}/{path...}`, so registering both panics. The assets are dispatched ahead of the mux instead — and `assets` is one of the reserved infrastructure names in `docs/architecture/urls-and-identifiers.md` §6.9, so a repository can never be called that and the prefix cannot shadow a real path.
  - **A directory listing was served and is now refused.** `http.FileServerFS` lists a directory by default, so `/assets/` returned `200` and enumerated the build's file names. An asset path is not a page and a listing is not part of the interface.
  - **The shell is server-rendered and says something before the bundle runs**, including a `<noscript>` line, and it reports the build commands rather than serving a blank page on a checkout where the frontend has not been built. An unbuilt frontend is not fatal: the read surfaces still work, which the test asserts.
  - **The boot payload carries message text by identifier rather than literal English**, in a `application/json` script element rather than an inline script, so no executable code is assembled from data and the content security policy needs no exception for it. The session token never travels: the cookie is `HttpOnly` so a script cannot read it, and a test asserts the document does not echo it.
  - **The stylesheet import precedes the component imports in `main.tsx`**, because a bundler may otherwise inline the CSS into JavaScript instead of emitting a file the shell can link.
  - **The bundle budget is implemented as the document names it.** `docs/architecture/performance.md` §3.4 names `web/scripts/check-bundle-size.mjs`, gives the per-budget values, and states the 10% tolerance and the largest-twenty-by-gzip output. The script implements that, plus the two build-output rules the same section states: source maps are not shipped, and a route does not statically import another route's chunk.
  - **A hardcoded-string check runs in CI, as `frontend.md` asks.** Its first version reported TypeScript type arguments (`useState<…>`, `as Partial<…>`) as user-visible text; a check that cries wolf is a check that gets ignored, so the pattern was narrowed to genuine JSX text nodes.
  - **Two limits are honest and stated rather than hidden.** First, the build and the client test suite do not run on a machine whose sandbox refuses esbuild's child process (esbuild starts a platform binary and talks to it over pipes); they run in CI, which is why `web-build` exists as a separate job. Second, a client holds the CSRF token from the sign-in response, so a **page reload loses the ability to submit a form until the reader signs in again** — a direct consequence of the token being a stored digest the server cannot re-derive. W1.9c-2 removes this by deriving the token from the master key.

##### W1.9c-2 CSRF over a page load and the settings surface
- **Status:** implemented
- **Ticked in this change, with the evidence:** four parity lines that were waiting on the browser path this workstream delivers.
  - **Change visibility between public and private with the required confirmation.** The confirmation rule is tested in eight shapes (absent, the wrong word, the acknowledgement word where the name is required, a name prefix, the name, another case, padded, and the full `owner/name` form), and end to end on a real instance: the refusal names the `confirmation` field and says what to type, the repository is unchanged, the confirmed change returns `200`, and an anonymous read then succeeds — the transition's observable effect rather than a field in a payload.
  - **Change the default branch.** Tested at the service, through the API's `PATCH`, for the audit record's detail, for idempotence, and on an archived repository where it must still work.
  - **Archive and unarchive a repository (read-only when archived).** The strongest evidence in the project: a real `git push` from a real client is accepted before archiving, refused after it with a message naming the archive state, the branch **does not move**, a fetch still succeeds, and an anonymous clone of an archived public repository still works. - **The plan recorded here before this workstream was wrong, and the documents say so.** The earlier note said the master key would let the CSRF token be "a signed value the server derives rather than a digest it stored". Three documents refuse that:
  - `docs/architecture/secrets.md` puts the CSRF token in the **hashed** category: "High-entropy random token (session, CSRF, invitation, …) → SHA-256 digest", and states the rule behind it — "**A value that the server only ever compares is hashed, never encrypted.** Comparing a digest needs no key and cannot be reversed." A CSRF token is only ever compared, so hashing it is the prescribed storage and a key has no part in it.
  - `docs/security/threat-model.md` T-K4 requires a token "**bound to the session**". A value signed with an instance key is computable by anyone holding the key and is not bound to a session; a derived value would also be derivable from the session cookie, collapsing two independent secrets into one.
  - `docs/architecture/secrets.md` prescribes constant-time comparison "for a CSRF token accompanying an already-resolved session", which is the digest comparison the implementation already performs.
  - **What actually caused the reload limitation** was neither of those: it was that only the digest is stored, so the token behind it cannot be recovered and a browser that lost it could not be handed the same one again. The fix is to **issue a new one** from the document render, which is what this workstream does. `- **Notes:**` follows.
- **Notes:**
  - **A page load now issues the token**, so a reload no longer loses the ability to submit — the limitation W1.9c-1 recorded and stated as honest is removed. `RotateCSRFToken` resolves the session, generates a token, and writes only its digest, in one statement scoped to a live unrevoked session so a rotation cannot resurrect a session revoked in between.
  - **At most one token is live per session at a time.** Issuing replaces the previous digest, which is the storage the document prescribes. Two documents open from one session therefore share one live token and the later one's is valid; a request presenting the superseded token is refused like any other invalid token. That is a real tradeoff, recorded rather than hidden, and it is the cost of keeping a single digest rather than a digest per token.
  - **The settings surface takes the confirmation word from the server.** It is carried in the boot payload from `repository.VisibilityConfirmationWord`, so a client never holds its own copy of a policy value — a client that did would tell the reader to type something the server rejects the moment the rule changed.
  - **The settings shell discloses nothing.** It names only the two path segments the caller already typed, and its boot payload's key set is asserted exactly, so a field added later that carried repository contents would fail a test rather than pass a substring search. The repository's visibility, branch, archive state, and grants come from the API, which decides per caller.
  - **A field-level refusal is rendered against its field.** The API's `errors` array names each rejected field, and the surface attaches each message to its input with `aria-invalid`, rather than collapsing them into one banner that leaves the reader hunting.
  - **Two gates can only run in CI.** The frontend build and the client test suite cannot run in the development sandbox, so the settings surface's own tests and the production build are exercised by the `web-build` job. What runs locally is the Go suite, the client typecheck, and the hardcoded-string lint. The one end-to-end test that needs a rendered document skips with that reason rather than passing on a weaker path; the token-submission half is covered unconditionally through the API.
  - **`GITNEST_SECRET_KEY` is deliberately not implemented, and this is a decision for a maintainer.** `docs/architecture/secrets.md` says the process refuses to start without it, but the same document defines what it is for: "**A value that the server must replay is encrypted**", listing OAuth client secrets, App private keys, webhook signing secrets, SMTP passwords, object-storage secrets, SAML keys, CI secret values, and workspace secrets. **None of those exist in phase 1**, so a mandatory startup key would today encrypt nothing while adding a required operator step, a required value in every deployment and test, and a value that is documented as unrecoverable if lost — a liability to rotate for no benefit. The correction proposed is to introduce the key in the workstream that first stores a replayable secret, at which point its consumers make it meaningful. Implementing "the process refuses to start" without it would also break `docker compose up`, the CI environment, and the whole test harness, which is why it is reported rather than done.

### W1.11 Git LFS
- **Status:** split into W1.11a and W1.11b. **Both are implemented.**
- **Deliverable:** the LFS batch API, object upload and download authorized through the repository service, and a local-disk object store addressed by content hash.
- **Depends on:** W1.5, W1.6, W1.7
- **Why it is split:** the workstream has two halves with different dependencies. The content-addressed object store needs only the storage layout and is where the integrity and enumeration controls live (T-C4, T-C3's storage half), while the batch API needs a schema — an object's existence has to be recorded per repository so a batch can answer without walking the disk — and the database was not available this round. Delivering the store first also means the API is built on a layer whose refusals are already tested.

#### W1.11a Content-addressed LFS object store
- **Status:** implemented
- **Delivered:** `internal/platform/storage/lfs.go` — `LFSPath`, `LFSObjectExists`, `LFSObjectSize`, `OpenLFSObject`, `StoreLFSObject`, `RemoveLFSObject`, `RemoveLFSRepository`, `ListLFSObjects`, `CleanupLFSStaging`, and `ValidateOID` — plus the startup sweep wired into `internal/app`.
- **Notes:**
  - **The path is derived, never accepted.** `docs/architecture.md`: object storage "is addressed by a content hash rather than a user-supplied path". An object lives at `<root>/lfs/<storage_id>/<aa>/<bb>/<oid>`, so both the repository identifier and the digest are validated before anything touches the filesystem — the identifier must be a canonical UUID and the digest exactly 64 lowercase hexadecimal characters. Lowercase only, deliberately: accepting both cases would create two names for one object, and silently normalizing a client's identifier would hide a client defect. Traversal cannot even be expressed, because the length check refuses it before the containment check runs.
  - **Cross-repository isolation is structural.** T-C3 requires that objects be "served only for a repository the principal can read" and be "addressed by verified content hash". The authorization half belongs to the repository service. The store implements the other half: an object lives under the *requesting* repository's storage identifier, so a caller who holds a valid digest belonging to another repository finds nothing. A test stores an object for one repository and asserts that a valid digest is unreachable under another, so a digest is demonstrably not a capability.
  - **Integrity is verified during the stream, before the object is reachable.** T-C4: "the declared size and digest are verified against the received bytes before the object is finalized; a mismatch rejects the object and leaves no entry." The bytes are streamed once into a staging file while the running digest and length are computed, and only a match triggers the rename. Tests cover a wrong digest, a wrong size, an undeclared size (where the digest alone must still refuse), a body that fails partway, and an oversized one — each asserting that neither the object nor a staging file survived.
  - **The oversized case does not read the whole body.** One byte past the cap is read deliberately, so an over-limit upload is refused having written only the cap, rather than being buffered and then rejected. This matters because the documented cap is 2 GiB.
  - **Staging is inside the storage root, not the temporary root.** `performance.md` requires it: "Uploads write to a temporary path inside the storage root ... and rename into place." A rename across filesystems is not possible and a copy would not be atomic, so the temporary root — which belongs to Git operations — is the wrong place. A test asserts LFS never stages there.
  - **The startup sweep is T-C5's restart half.** Each upload removes its own staging file on every exit path, so the sweep exists for a process killed mid-upload. It reports rather than fails: stale staging data is a disk-space concern, and refusing to start over it would turn a cleanup problem into an outage.
  - **Bounds come from configuration, as the document gives them.** `performance.md` names the cap `git.lfs_max_object_bytes` (2 GiB) rather than a constant, so `LFSOptions` carries it with `DefaultLFSOptions` and a `Validate` that fails at startup rather than on the first upload.
  - **A gap in the data model, reported rather than papered over.** `docs/architecture/data-model.md`'s core entity map has no LFS group, while every other document places LFS in phase 1 — `architecture.md` describes the store, `urls-and-identifiers.md` gives the routes as "Git LFS (phase 1)", and the parity line is P1. **The table an object's existence is recorded in is therefore undesigned.** This workstream deliberately did not invent one; it would need an owner to decide whether existence is authoritative in a table, derived from the disk, or both with a reconcile. W1.11b needs that decision.
  - **`data-model.md`'s quota is also unimplemented.** `performance.md` states `GIT-LFS-QUOTA` as "LFS bytes per repository: 50 GiB", checked "under a transaction lock" — which belongs with the batch API, where a repository's current usage is known, rather than in the store.
- **Verification:** 13 new tests, all passing (`go test ./internal/platform/storage/...`), plus the full suite green in no-database mode.

#### W1.11b LFS batch API and HTTP surface
- **Status:** implemented (the per-repository quota is enforced best-effort; see the gap below)
- **Delivered:** `internal/transport/http/git/lfs.go` — `POST /{owner}/{repo}.git/info/lfs/objects/batch`, `PUT` and `GET /{owner}/{repo}.git/info/lfs/objects/{oid}` — registered from the same `Register` call as the smart-HTTP routes so LFS shares that handler's authorization path, storage layout, and authenticator. Plus `storage.LFSOptions.RepositoryBytes`, `Layout.LFSUsage`, and `Handler.WithPublicURL`.
- **Ticked in this change:** `Git LFS batch API, upload, and download addressed by content hash — P1`. Evidence: **the real `git-lfs` 3.7.1 binary drives a batch negotiation and an object upload against these endpoints, and the bytes it sent are the bytes the store holds and serves back.** Plus a full protocol round trip over HTTP, the per-object refusal shapes, and the cross-repository and denial cases.
- **Notes:**
  - **The real client found a bug no hand-written request would have.** The batch originally returned a *relative* action href, on the reasoning that the protocol permits it and that it avoids building a URL from the client-controlled `Host` header. `git-lfs` refuses it: `missing protocol: "alice/writable.git/info/lfs/objects/<oid>"`, and the transfer never happens. The href is now absolute, built from the configured `GITNEST_PUBLIC_URL` — which is also the correct value behind a proxy, where the request's `Host` is not the URL the client used. The Host fallback remains only for a handler that was never given a public URL, and the response is `no-store`, so it cannot be used to poison a cache. **This is why the conformance test was worth its setup cost.**
  - **The client is driven with `push --object-id`, and the object is placed in its local store directly.** `git add` cannot run in this sandbox: the clean filter needs `sh.exe`, whose signal pipe the sandbox refuses (`Win32 error 5`). The local store's layout (`lfs/objects/<aa>/<bb>/<oid>`) is documented, so writing there is faithful to what the filter produces, and the batch negotiation and the upload — the parts under test — are still driven entirely by the real client.
  - **Authorization is the same call the clone and push paths make.** Every route calls `authorize()`, so T-A4's "the same not-found shape as a nonexistent repository" is inherited rather than restated, and a test asserts the denied body and the nonexistent-repository body are byte-identical.
  - **The batch's operation picks the level, and the body is read before it can.** A batch says `download` or `upload` in its body, so the body is parsed before the access question is asked; an upload requires write, which is what makes an archived repository refuse it through the same rule a push hits. A test asserts a read-only caller's upload batch is refused while its download batch on the same repository succeeds.
  - **One bad descriptor does not fail a batch.** A malformed digest or a missing object is reported against that object, so a client with a thousand objects retries the rest instead of renegotiating everything.
  - **Holding a valid digest is demonstrably not a capability.** The store scopes objects to the requesting repository's storage identifier, so an object stored for one repository is unreachable under another even though its digest is well formed and its bytes are on disk. Both the batch and the direct object URL are asserted, because a client can skip the negotiation.
  - **The size limit is reported clearly**, which is what testing.md asks of this row: a `413` whose LFS envelope names the limit, distinguishable from the quota refusal.
  - **A quota refusal is not an oversized-object refusal**, because the two call for different client behaviour — one splits the file, the other has nowhere to put it.
- **The one gap: the per-repository quota is best-effort under concurrency.** `performance.md` specifies `GIT-LFS-QUOTA` as checked "under a transaction lock", which needs a per-repository counter that `data-model.md` does not define. The check is implemented against the bytes actually on disk, so it stops one client filling the disk, but two uploads passing it at the same moment can both land. That is recorded rather than hidden, and the exact version awaits the schema decision already reported. Computing the usage walks the repository's object tree, so its cost grows with the object count — a second reason the counter is worth having.
- **Verification:** 39 LFS tests passing with zero skips, including the real-client case; the full suite green in no-database mode.
- **Acceptance:** a repository using LFS clones and pushes through a real Git client; an unauthorized caller cannot fetch an object by hash; a size limit is enforced and reported clearly.

### W1.12 Backup and recovery
- **Status:** implemented
- **Delivered:** `internal/backup` (the recovery set: capture, verify, restore), `internal/platform/pgdump` (the `pg_dump`/`pg_restore`/`psql` adapter), the `gitnest backup`, `gitnest backup-verify`, and `gitnest restore` commands, and [../operations/backup-restore.md](../operations/backup-restore.md).
- **The conflict this exposed, and how it resolves.** `docs/reference/events.md` marks the backup events as **phase 10**, and parity line 574 ("Coordinated backup, restore drill, and disaster-recovery runbooks") is **P10**, while the implementation plan lists backup in phase 1. [../roadmap/10-operations-and-scale.md](../roadmap/10-operations-and-scale.md) W10.11 settles it: its deliverable is "One documented recovery set that treats the PostgreSQL database, repository storage, and object storage as a coordinated unit, **built from the earlier backup work**". So phase 1 is the single-node procedure and phase 10 extends it with coordination, locking, object storage, and runbooks. **That is why the parity line stays unticked**: it asks for the coordinated set and the runbooks, and ticking it now would claim them.
- **Notes:**
  - **One directory, one manifest**, per [../architecture.md](../architecture.md) section 8: "Database and repository-storage backups are one recovery set with one documented procedure." The manifest records the dump's size and SHA-256, the storage copy's file count and bytes, and one entry per repository the database knew about — which is what makes the set *verifiable* rather than merely present.
  - **The LFS objects come for free, and that is the reason for the layout.** They live under `<repository root>/lfs`, so one copy of the repository root captures them and there is no second path an operator can forget. A test asserts the LFS object is in the set, because "dump the `.git` directories" is the naive backup that would lose it.
  - **A capture that finds the instance already inconsistent does not refuse to finish.** This was a real defect a test found: the first version failed the whole capture when one repository's directory was missing, discarding the backup of every other repository — the opposite of what an operator in trouble needs. Findings are now classified: one about the **set** makes it unusable, one about the **instance** is recorded, reported, and the capture proceeds.
  - **Verification reports every problem, not the first**, and the documentation states what it can and cannot prove: it cannot show a repository's object graph is undamaged (`git fsck` is that step) and cannot show the dump restores (only the drill is that).
  - **The restore verifies before it overwrites**, and restores the database before the storage: a repository row whose bytes arrive second is repairable, while bytes whose row never arrives are invisible to the instance.
  - **The target rules are refusals, not warnings.** Inside the repository root means each capture would copy the previous set; inside the temporary root means the startup sweep would delete the backup.
  - **The password never reaches an argument vector.** `administration.md` requires it — "arguments are visible in the process table and shell history" — so there is no `--database-url`, the DSN comes from the environment, and `pgdump` moves its parts into `PG*` variables. A test asserts the password is not rendered and that the redaction is *visible* rather than the variable being absent.
  - **`--confirm` is required to restore**, and `pg_dump` runs without `--schema=public`: naming one schema would silently produce an empty set on a database whose objects live elsewhere. An empty dump is separately refused, so a dumper that exits zero having written nothing cannot pass as a backup.
  - **The verification found an environment fault that had been masking test results.** The drill's clone failed with `Failed to connect to 127.0.0.1 ... via 127.0.0.1`, which is git routing through a **proxy**: the developer's `~/.gitconfig` sets `http.proxy`, and `GIT_CONFIG_NOSYSTEM=1` skips only the *system* file. `internal/platform/git` already points `GIT_CONFIG_GLOBAL` at the null device for the production runner; the tests did not, so a personal setting could decide whether the suite passed. They now do — which also explains why the Git-over-HTTP tests passed in one round and could not in the next, once the proxy process stopped.
  - **The Windows permission reality is documented rather than implied.** The capture writes `0700`/`0400`, but NTFS does not carry POSIX bits: a directory reports `0777` whatever mode was requested, while the read-only attribute is honoured so an artifact cannot be edited in place. The test asserts what each platform actually provides.
- **Acceptance evidence:** 25 tests passing with zero skips — 15 in `internal/backup` and 8 in `internal/platform/pgdump` — including `TestTheDrillLosesNothing`, which captures a real Git repository and a real LFS object, destroys the storage, restores from the set, runs `git fsck --strict` on the restored repository, and **clones it over HTTP with the real `git` client**. Both CLI refusals (`--target`, `--confirm`) produce usage and a non-zero exit.

- **Status:** implemented
- **Delivered:** `Dockerfile`, `deploy/gitnest.service`, `deploy/gitnest.env.example`, `deploy/README.md`, the `gitnest health` command, `internal/platform/systemd` (the readiness notification), the migration preflight (`gitnest migrate --status` / `--dry-run`), README sections for deployment, health, and upgrading, and the `container-build` CI job the packaging document names.

- **The container's health check is the binary, not `curl`.** `packaging.md` section 7 requires the image to carry "only the binary, the runner agent where applicable, the Git executable and its runtime dependencies, and CA certificates" and explicitly excludes a package manager cache, so adding `curl` for the `HEALTHCHECK` would violate the size discipline. `gitnest health` probes `/api/health` by default and `/api/ready` with `--ready`, exits non-zero unless the endpoint answers 200, and carries the endpoint's own message so an operator learns *why* rather than only that it is unhealthy. It also resolves the configured listener, mapping a wildcard bind to loopback, because a probe against `0.0.0.0` cannot connect and would report a healthy instance unhealthy.
- **The migration preflight is read-only, which is what makes it usable as a gate.** `packaging.md` section 11 step 4 names `--status` and `--dry-run`; both probe the ledger rather than creating it, take no migration lock, and apply nothing, so they are safe against production. `--dry-run` exits non-zero when the database is **ahead** of the binary — the state a rollback to an older binary leaves — and it reports the status *before* returning the error, so the operator sees which migrations are the problem.
- **The socket-bound notification tests run on Linux only.** Windows cannot create a unix datagram socket, so six tests skip there; the encoding properties that matter (a value cannot forge a field, control characters are dropped, a field is bounded) are asserted against the message builder directly, which is why they are separated from the transport. Thirteen tests pass here, six skip.
- **What is not delivered, and belongs to later phases:** the `worker` and `ssh` run modes and their units (phases 5 and 2), multi-architecture image publication and artifact signing (`packaging.md` section 4), reproducible-build verification (section 6), and the release smoke-test transcript (section 8). The signing and reproducibility work needs a release pipeline that does not exist yet.
- **Verification:** 17 new tests passing — 9 for the health command, 8 for the deployment artifacts, plus 13 for the systemd notification (6 socket-bound ones skip on Windows). The full suite is green in no-database mode across 19 packages, and the CI workflow parses with all 8 jobs.

### Styling for the server-rendered read surfaces
- **Status:** implemented
- **Delivered:** `internal/transport/http/web/static/gitnest.css` (the token set and every rule), `internal/transport/http/web/static.go` (the embedded asset and its cache key), the `StyleSheets` wiring at both page-construction sites, and `Handler.StaticHandler`.
- **Why it was outstanding, and what closed it.** The read surfaces carried no stylesheet at all: `layout.html` had a `StyleSheets` field that was never populated, so the pages that make up most of the product rendered as unstyled HTML. `frontend.md` requires "design tokens with a light and dark theme, both driven by one token set", which only the interactive surfaces had.
- **One token set, machine-checked.** The stylesheet is embedded in the binary rather than built by Vite, deliberately: these are the pages `frontend.md` requires to be complete on first byte, and this project keeps them working on a checkout where the frontend has not been built, so styling them from the Vite bundle would give their appearance a dependency the pages do not otherwise have. That makes two files by necessity, so a test **compares their token values** and fails when either side adds or changes one — which is what makes "one token set" a fact rather than a promise. It caught real drift immediately: `--surface` existed only on the read side.
- **Contrast is computed, not asserted.** A test parses the token blocks and computes the WCAG contrast ratio for each foreground token against the surface it is used on, in both themes, with the helper itself checked against WCAG's worked examples (black on white is 21:1). `--border` is held to a visibility floor rather than WCAG's 3:1, and the reason is recorded in the test: a hairline rule between table rows carries no information, so holding a decorative separator to a component-boundary floor would force a darker palette for no accessibility gain.
- **Both themes, three ways to select one.** Light is the default, `prefers-color-scheme` supplies dark, and `[data-theme]` overrides either explicitly so a future toggle needs no second sheet. A test asserts the two dark blocks agree, because a reader who chose dark deliberately must see what a reader whose system chose it sees.
- **One real bug, and it was subtle.** `http.FileServerFS` resolves the full `r.URL.Path` against its filesystem. The asset filesystem is rooted at `static/`, so an unstripped `/static/gitnest.css` was looked up as `static/gitnest.css` inside it and answered by the file server's own 404 — which reads as "the asset is missing" rather than "the handler is wrong". The frontend assets escape this only because their prefix `/assets/` happens to be the directory name inside `dist`, which is a coincidence rather than a design; the comment records both halves. The fix is `http.StripPrefix`.
- **The routing conflict recurred, and the dispatcher was already the answer.** `GET /static/` cannot be registered on the mux: it is a subtree pattern that conflicts with `GET /{owner}/{repo}/tree/{ref}/{path...}`, and `net/http` panics on two patterns neither of which is more specific. It uses the same ahead-of-the-mux dispatch the frontend assets use, and a test chains it explicitly so the arrangement is exercised.
- **The accessibility gate frontend.md requires now exists for the read surfaces.** It is structural rather than a browser-driven audit — there is no browser here — and it asserts what such an audit flags in a page with no script: a document language, exactly one first-level heading, a skip link whose target exists, landmarks, a caption on every table, a viewport that permits zoom, no inline style, and every link having a textual name. That last check is what keeps an icon-only link from being announced as "link" with nothing to act on.
- **Ticked in this change:** `Light and dark themes`. Evidence: both themes are defined from one token set, the two stylesheets' token values are asserted equal, and the contrast ratio of every foreground token is computed and checked in both. The stylesheet is served over a real listener as `200`, `text/css`, `max-age=31536000, immutable`, with the build's hash in the URL.
- **Not ticked: `Keyboard-usable navigation across the primary surfaces`.** The server-rendered pages are keyboard-usable by construction — no script, native elements, a skip link, and a `:focus-visible` ring — and a test asserts the skip link targets a real region. But the line says *primary surfaces*, which includes the interactive ones whose keyboard walkthrough is asserted by a client test that **cannot execute where esbuild's child process is refused** (see the note on that sandbox above; the `web-build` CI job runs it). The box stays unticked until that evidence exists.
- **Verification:** 10 new tests passing with no skips, 8 of them with subtests, plus the full suite green in no-database mode across 19 packages.

### W1.14 Personal access tokens
- **Status:** implemented
- **Why it exists, and why it is phase 1.** The plan was internally inconsistent: this file's own Scope section lists "Accounts and their credentials, browser sessions and **personal access tokens**" as phase 1, and its Exit criteria require that "an invited contributor can sign in, create a private repository, push a local branch, browse the result, and clone it from a second working copy" — **but no W1.x workstream delivered one**, so every Git caller resolved as anonymous and the exit criterion was unreachable. Against that, `docs/reference/events.md` marks `token.created` as phase 4 and `docs/roadmap/04-api-and-extensibility.md` W4.8 owns the full model. **The exit criteria win**, because they are the phase's gate, so the minimum a pusher needs is delivered here and the rest stays with W4.8. The split is: this workstream has a classic `repo`-scoped token, revocation, and the Git credential path; W4.8 keeps fine-grained tokens, resource selectors, scope strings beyond `repo`, expiry policy, and the last-used instant.
- **Delivered:** `migrations/0006_personal_access_tokens.up.sql`, `internal/identity/token_access.go` (the types, validation, and prefix handling), `internal/identity/token_service.go` (creation, resolution, revocation), `internal/identity/postgres_tokens.go` (the store), `internal/transport/http/git/token_auth.go` (the credential path), and the wiring in `internal/app`.
- **The defect this uncovered, which was the real blocker.** A real `git clone` failed even though the handler's own tests passed, because **Git does not send a credential first**: it sends an unauthenticated request and presents credentials only after a `401` carrying `WWW-Authenticate`. The transport answered an anonymous caller with a plain `404`, so a real client **never sent its token at all** — a deployed instance could not authenticate any pusher, which is exactly the exit criterion that was stuck. Anonymous callers are now challenged. This is compatible with T-A4 rather than a weakening of it: the rule forbids a caller *holding a usable credential* learning that a repository it may not read exists, and that caller still reaches the not-found branch. The challenge is byte-identical for every repository on the instance, so it distinguishes nothing, which a test asserts by comparing status, `WWW-Authenticate`, and body between a private repository and a nonexistent one.
- **Notes:**
  - **Only the digest is stored**, per `secrets.md`: a personal access token is in the hashed category with the session and invitation tokens. The display prefix is stored in the clear because `administration.md` requires an administrator to revoke "by its display prefix", and twelve characters is far too little to be a credential.
  - **The value is returned once and is unrecoverable afterwards.** A test asserts the store holds a digest and not the value, another asserts a listing cannot reconstruct it, and the type a transport receives has no field for either.
  - **A revoked token fails on the next request**, and an unknown token is refused indistinguishably from a revoked one, so a refusal is not an oracle.
  - **A disabled account's token stops working**, which is what makes `administration.md`'s "Disable is preferred over delete" true.
  - **An unknown scope is refused rather than dropped**, and the database refuses to store a scope the code does not enforce, so a token can never carry a restriction that is not applied.
  - **Revoking by prefix refuses an ambiguous match** and reports the count, because a destructive action taken on a guess is worse than refusing.
  - **Three credential forms are accepted** — `Bearer`, `token`, and `Basic` — because a credential helper and a prompt put a token in different places, and refusing either would make a token unusable from the command line.
  - **The credential never reaches a log line**, asserted with the token travelling in a URL, which is the shape most likely to leak because a naive access log records the whole request line.
  - **A defect the array column exposed.** `personal_access_tokens.scopes` is the project's first `TEXT[]`, and the pgx stdlib driver fills neither `*[]string` nor `*pgtype.Array[string]` on a read. The read side now asks the database for `array_to_string(scopes, ',')`, which avoids writing a PostgreSQL array-literal parser in Go for a column whose contents this package controls.
- **Ticked in this change:** `Personal access token creation showing the value once`. Evidence: 18 identity tests and 10 transport tests, plus six end-to-end tests including `TestAnInvitedContributorPushesWithAToken` — a real `git clone`, commit, and push authenticated by a token issued through the real service and stored as a digest in PostgreSQL, then read back from a second working copy.
- **Verification:** the full suite passes with `-race` against a real database across 19 packages, with no leftover schemas.

## Security notes

- Every access decision comes from the repository service; the Git transport, the API, and the browser must not answer it independently.
- Repository paths derive from internal IDs. A client never supplies a path.
- Git processes are invoked with argument arrays, a controlled environment, limits, and no shell.
- Archive, diff, and LFS operations are bounded by size and time.
- Session cookies are `Secure`, `HttpOnly`, and `SameSite=Lax`; state-changing browser requests require a CSRF token; session tokens never go to browser storage.
- Rendered repository content is untrusted: raw HTML is disabled and all output is escaped.
- No repository-provided hook is ever executed.

## Out of scope

Organizations, teams, and inherited permissions (phase 2). Issues and pull requests (phases 2 and 3). SSH Git transport (phase 2). Branch protection and rulesets (phase 8). Repository-scoped packages (phase 6). Pages and wikis (phase 7). Search (phase 7).

## Exit criteria

A fresh instance can be bootstrapped by an operator. An invited contributor can sign in, create a private repository, push a local branch, browse the result, and clone it from a second working copy. The owner can grant and revoke collaborator access. Anonymous users can read public repositories but cannot read private ones or infer their existence. Tests exercise denied access through every implemented transport. A tested backup restores the instance.

Do not start phase 2 work until these checks pass and are recorded in the implementation plan's status table.
