# Packaging, release, and upgrade

**Status:** Target design. Nothing in this document is implemented; the implementation code is being rebuilt from the documentation, and every statement here describes the intended design.
**Scope:** How GitNest is built, versioned, released, installed, and upgraded: the built React assets, the build pipeline, release artifacts, version identification, reproducible builds, the container image, the system-service deployment, the upgrade and rollback rules, the schema and binary support policy, and pre-publication release verification.

Related documents: [architecture.md](../architecture.md) (module boundaries, runtime topology), [frontend.md](frontend.md) (what the built assets contain), [configuration.md](configuration.md) (startup configuration versus instance settings), [../product-goals.md](../product-goals.md) (exclusions, definition of done), [../roadmap/10-operations-and-scale.md](../roadmap/10-operations-and-scale.md) (W10.10 upgrade tooling, W10.11 backup, W10.14 zero-downtime release), [../roadmap/01-identity-and-repository-hosting.md](../roadmap/01-identity-and-repository-hosting.md) (W1.13 deployment skeleton).

## 1. Conventions used here

| Term | Meaning |
| --- | --- |
| Release version | `MAJOR.MINOR.PATCH`, optionally with a prerelease suffix (`-rc.1`). Recorded in the binary and in the release manifest. |
| Build version | The release version plus the commit. The identity the binary reports and logs. |
| App version | The database schema version a binary expects: the count of applied forward-only migrations, exposed as an integer. |
| Minimum supported database version | The oldest app version a binary can serve without migrating. |
| Artifact set | Everything published for one release tag: binaries, the runner agent, checksums, the container image, and migration compatibility notes. |

A release is published from a signed tag on the main branch. No artifact is published from a working tree, a dirty checkout, or a commit that failed any gate in section 3.

## 2. How the built React assets reach a running instance

The React application lives in `web/` and is built by Vite into `web/dist`. The Go process must then serve that output same-origin with the API, with no Node.js runtime present on the instance. Three options were considered.

| Option | How it works | Advantages | Costs and failure modes |
| --- | --- | --- | --- |
| **A. Embedded in the binary** | A build step copies `web/dist` into a generated Go source tree that a `//go:embed` directive references, so the assets are part of the binary. | One artifact per platform describes the whole instance. Moving the binary moves the UI; no path configuration can be wrong. Checksums and the container image cover the assets. The binary self-reports exactly which UI it serves. | The binary grows by the size of the built assets. An asset-only fix needs a full release. A custom build needs the frontend toolchain at build time. |
| **B. Installed beside the binary** | The release ships a directory that must be placed next to the executable; the binary resolves `web/dist` relative to its own path. | Smaller binary. Assets can be replaced on disk without touching the executable. | Two artifacts must stay in step, so a partially applied upgrade serves assets from one version and APIs from another. Path resolution depends on how the process was started. Rollback has to roll back both. |
| **C. A directory referenced by configuration** | `GITNEST_WEB_ASSETS_DIR` names a directory; the binary serves whatever it finds there. | Assets can be updated or themed independently. Several web nodes can share one asset directory. | The running version and the served UI can differ silently, and the API contract they share can drift. Installation grows a mandatory extra step and a second thing to back up and monitor. |

**Recommendation: option A, assets embedded in the binary, with option C retained as an explicit, logged development and escape-hatch override.**

The deciding reason is the single-node install promise: one binary, PostgreSQL, Git, and a data directory. One artifact means `--version` fully describes what is running, an upgrade is one file swap, and a rollback is one file swap back. Options B and C trade that away for a flexibility no operator requirement asks for, while introducing the one failure mode that is hardest to diagnose from logs: a UI that does not match the API it calls.

Rules for option A:

- What is embedded is the whole release asset set, not only the React bundle: the Vite build output (hashed, immutable JS and CSS) plus the Go HTML templates that render the server-rendered read surfaces. [frontend.md](frontend.md) fixes that split; this document only decides how those bytes reach the instance.
- The generated embed tree holds only build output; it is generated by the build, committed as an empty placeholder, and never edited by hand.
- `GITNEST_WEB_ASSETS_DIR`, when set, overrides the embedded assets. Startup logs one line recording which source is being served at which build version, and fails fast if the directory does not exist or has no `index.html`. This exists so a maintainer can iterate on assets against a release binary without rebuilding it; it is not the supported production path.
- Hashed asset filenames are served with immutable caching; `index.html` is served `no-cache`, and unknown non-API paths fall back to it for client-side routing.
- The development workflow stays Vite-based: `vite dev` serves the application on its own port and proxies `/api` and Git routes to the Go process, which runs in the ordinary `serve` mode. Hot module replacement is the development loop. Embedding is a release-build concern only and must never be required to run the application locally.
- A CI job (section 9) fails if the embedded assets are stale with respect to `web/`, which is what stops an embedded-asset build from silently serving an old UI.

## 3. Build pipeline

One repository, one pipeline definition, several stages. `make` targets and the CI workflow invoke the same commands so a local run matches CI.

| # | Stage | Command (canonical form) | Fails on |
| --- | --- | --- | --- |
| 1 | Format check | `gofmt -l cmd internal migrations` | Any output; also CRLF line endings |
| 2 | Vet | `go vet ./...` | Any diagnostic |
| 3 | Generate check | Regenerate API and asset artifacts, then `git diff --exit-code` | A committed generated file that is stale |
| 4 | Build (Go) | `go build ./...` | Any build error |
| 5 | Unit tests | `go test ./...` with the race detector | Any failure; integration tests skip when no DSN is set |
| 6 | Integration tests | `go test -race ./...` with `GITNEST_TEST_DATABASE_URL` set | Any failure; skipped without a database |
| 7 | Frontend build | `npm ci --prefix web` then `vite build` | Build or type error |
| 8 | Frontend lint | ESLint plus `tsc --noEmit` | Any error; warnings are a review topic, not a gate |
| 9 | Frontend tests | Component tests and end-to-end tests against a built binary | Any failure |
| 10 | Asset freshness | Compare the built `web/dist` digest with the embedded tree | A stale embed |
| 11 | Container image build | Build the multi-stage Dockerfile for the release platforms | Any build failure |
| 12 | Reproducibility check | Build the Go binary twice from the same commit and compare SHA-256 | Differing binaries |
| 13 | Release smoke test | Run the image against a real PostgreSQL and a real Git client (section 8) | Any failed step |

Stage ordering is dependency order. Stages 1-2, 5-6, and 7-8 are independent of each other and may run as parallel jobs.

### 3.1 Pull request versus release

| Stage | Every pull request | Release (tag) |
| --- | --- | --- |
| 1 Format check | Yes | Yes |
| 2 Vet | Yes | Yes |
| 3 Generate check | Yes | Yes |
| 4 Build (Go) | Yes | Yes |
| 5 Unit tests | Yes | Yes |
| 6 Integration tests (PostgreSQL service container) | Yes | Yes |
| 7 Frontend build | Yes, once the frontend workstream is accepted | Yes |
| 8 Frontend lint and type check | Yes, same condition | Yes |
| 9 Frontend component tests | Yes, same condition | Yes |
| 9b Frontend end-to-end tests against a built binary | Not on every PR (kept on a nightly schedule) | Yes, blocking |
| 10 Asset freshness | Yes | Yes |
| 11 Container image build | Build only, no push | Build, tag, sign, and push to the registry |
| 12 Reproducibility check | Yes | Yes |
| 13 Release smoke test | No | Yes, blocking |
| Compose file validation | Yes | Yes |
| Documentation link and spelling check | Yes | Yes |

Rationale: a pull request proves the change compiles, is formatted, and passes tests against a real database. A release additionally proves that the artifact set is self-consistent and actually runs, because that is the difference between a commit and a thing an operator installs. Push of an image, creation of a tag, and upload of artifacts happen only in the release workflow, only from a protected tag, and only with a scoped, short-lived publishing credential.

## 4. Release artifact set

One release publishes:

| Artifact | Content |
| --- | --- |
| `gitnest_<version>_<os>_<arch>` binaries | `cmd/gitnest` for the supported platform matrix: `linux/amd64`, `linux/arm64`, `darwin/amd64`, `darwin/arm64`, `windows/amd64`. Each binary embeds the built web assets and the migration files. |
| `gitnest-runner_<version>_<os>_<arch>` binaries | `cmd/gitnest-runner`, same platform matrix, except `windows/*` only if the container runtime adapter supports it. Packaged separately from the server binaries so a runner host receives only what it needs. |
| `SHA256SUMS` | One line per artifact, sorted by filename, verified by the installer before use. |
| `gitnest_<version>_manifest.json` | Release version, commit, build time (from `SOURCE_DATE_EPOCH`), Go toolchain version, Node and Vite versions, app version, minimum supported database version, checksum of each artifact, and the container image digest. |
| Container image | `ghcr.io/<owner>/gitnest:<version>` and `:<major>.<minor>`, plus an immutable digest reference. Multi-architecture manifest for `linux/amd64` and `linux/arm64`. |
| `migration-compatibility.md` | For this release: the migrations it adds, whether each is additive or destructive, the expected duration and locking behaviour of each, the rollback classification per migration, the app version it leaves behind, and the versions it can be upgraded from or rolled back to. |
| Release notes | User-visible changes, required configuration changes, deprecations in flight, and any manual operator step. |

The runner agent is a separate artifact because it is a separate trust domain and is expected on hosts that never run the server. It shares the version number of the release it came from; a runner refuses to register when the control plane reports an incompatible protocol version and fails with a distinguishable error rather than running and misbehaving.

## 5. Version identification

Three values are compiled into the binary through `-ldflags -X` at link time:

| Value | Source | Purpose |
| --- | --- | --- |
| `version` | The release tag, or `dev` for a local build | Human-facing identity |
| `commit` | The Git commit the binary was built from | Exact provenance |
| `buildTime` | `SOURCE_DATE_EPOCH`, the commit timestamp | Reproducibility bookkeeping |

Rules:

- `gitnest version` (and `gitnest --version`) prints the build version, the commit, the Go toolchain version, the app version, and the build time, one field per line.
- Every run mode logs one structured startup line containing the build version, the commit, the app version, the run mode, and the `GITNEST_PUBLIC_URL`. No secret, DSN, or credential appears in it.
- The API exposes it at `GET /api/v1/meta`: `{"version", "commit", "build_time", "app_version", "api_version"}`. `/api/health` and `/api/ready` include the build version so a probe response identifies the release. No version surface exposes configuration values, database contents, or paths.
- A build with a modified working tree reports `dev` plus the commit and must not be published; the release workflow refuses to run outside a clean checkout at a tag.
- The operator-visible version and the app version are distinct on purpose: two releases may share an app version (no schema change), and an operator upgrading across several releases cares about the schema distance, not the marketing number.

## 6. Deterministic and reproducible builds

Requirement: two builds of the same commit with the same toolchain produce byte-identical binaries and matching SHA-256 checksums, so an operator can verify a published artifact from source.

Go rules:

| Rule | Reason |
| --- | --- |
| `go.mod` pins the toolchain exactly (`go 1.26.x` plus a `toolchain` line); the build uses `GOTOOLCHAIN=local` | A different Go patch level produces a different binary |
| `go.sum` is committed; module verification is on (`GOFLAGS=-mod=readonly`, `GONOSUMCHECK` never set) | The dependency graph is fixed |
| `-trimpath` on every build | Build paths do not leak into the binary |
| `CGO_ENABLED=0` for the published Linux binaries | No host C toolchain or glibc version in the result |
| `SOURCE_DATE_EPOCH` set from the commit time; wall-clock time is never embedded | Two builds at different times match |
| No timestamp, hostname, username, or absolute path in any generated file | Generated code is reproducible |
| Build cache and output paths fixed relative to the repository root | Path-independent output |

Frontend rules:

| Rule | Reason |
| --- | --- |
| `web/package-lock.json` is committed and the build uses `npm ci` | Dependency versions are frozen |
| The Node major version and the package-manager version are pinned in `web/package.json` (`engines`) and by the CI job's toolchain setup | The same versions build in CI and on a maintainer's machine |
| Vite is invoked through the pinned local dependency, never a global install | The bundler version is part of the build |
| The generated embed tree contains only hashed asset names, never paths or timestamps | Embedding stays deterministic |
| Two consecutive frontend builds from the same commit are compared for equality in CI | Catches an accidental content hash or timestamp |

A build that cannot pass the reproducibility check is a release blocker, not a warning. If a platform cannot be made reproducible, it is removed from the matrix rather than published with a caveat.

## 7. Container image

| Property | Decision |
| --- | --- |
| Build | Multi-stage: a Go build stage, a Node build stage for `web/dist`, and a runtime stage. The web stage runs once and its output is copied into every platform build. |
| Base image | A slim Debian-family runtime image that contains a Git executable and CA certificates, pinned by digest. The image must ship a Git new enough for the server to invoke; the exact minimum is recorded in the image and checked at startup. |
| Size discipline | Only the binary, the runner agent where applicable, the Git executable and its runtime dependencies, and CA certificates. No compilers, no package manager caches, no documentation. |
| User | Non-root, fixed UID/GID (`10001`), with a home directory that is not writable except for its own temporary area. The process never runs as root, in the container or under the system service. |
| Entrypoint | The `gitnest` binary directly (exec form), so signals reach the process and shutdown is bounded correctly. The image default command is `serve`. |
| Run modes | `serve` (default: web, API, Git over HTTP, webhook delivery), `worker` (background jobs), `ssh` (Git over SSH on the configured port). The runner agent is a separate image built from the runner stage. Mode selection is a subcommand, so the same image serves all three roles with a different argument. |
| Data directory | `GITNEST_DATA_DIR` (image default `/var/lib/gitnest`), containing the repository root, temporary Git operation space, and local blob storage. Mounted as a volume in every deployment. The image declares it as a volume so an operator who forgets to mount one sees the data in the container rather than silently writing elsewhere. |
| Migrations | Embedded in the binary. `gitnest migrate` needs no separate file mount. |
| Configuration | Environment only, plus optional file-backed secrets for the database DSN and secret key. No configuration file is required to start. |
| Health check | `HEALTHCHECK` against `/api/health` on the configured listener. Readiness is `/api/ready`, which reports database and dependency availability, and is what a load balancer or orchestrator should gate on. Neither endpoint requires authentication, and neither reveals configuration. |
| Ports | The HTTP listener (default 8080 in the image) and, for the `ssh` mode, the SSH listener (default 2222). |
| Logs | To standard output and standard error as structured lines. The image writes no log files, so an operator uses the platform's log collector. |
| Shutdown | `SIGTERM` begins a bounded shutdown: stop accepting, drain in-flight requests and Git operations, finish or release leased jobs, then exit. `SIGKILL` cleanup paths must leave no temporary Git data behind. |

Image tag policy: a release publishes an immutable `:<version>` tag, a moving `:<major>.<minor>` tag, and a digest. Deployments that care about exactness pin the digest; the manifest in section 4 records it.

## 8. Release verification before publishing

A release is verified against real infrastructure, not mocks. The smoke test runs in the release workflow against the built image and the built binaries, and its transcript is attached to the release.

| Check | Passes when |
| --- | --- |
| Migrate on an empty database | `gitnest migrate` applies every migration; a second run exits 0 and reports no pending migrations |
| Migrate from the previous release's schema | A database created by the previous release from the artifact set upgrades in one run, and `gitnest migrate --status` reports the expected app version |
| Concurrent migrate | Two `migrate` processes against one database apply each migration exactly once; the second waits on the migration lock or exits with a distinct "another migration is running" message |
| Start and probe | `serve` starts against a real PostgreSQL; `/api/health` returns 200; `/api/ready` returns 200 when PostgreSQL is reachable and 503 when it is stopped mid-run |
| Version surfaces | `gitnest version` and `GET /api/v1/meta` report the release version, the commit, and the app version, and the startup log line carries the same version |
| Embedded UI served | A plain HTTP GET of `/` from the running process returns the built `index.html` and a hashed asset, with no Node.js present in the image |
| Real Git client: clone | `git clone` of a seeded repository over HTTPS succeeds using the release binary's Git transport |
| Real Git client: push | A push over HTTPS creates a branch, and the pushed commit is readable from a second clone, so a fetch after a push is consistent |
| Real Git client: denied path | An anonymous clone of a private repository fails with a not-found response that does not disclose existence |
| Restart | The process restarts and serves the same repository without a migration or a manual repair step |
| Runner agent | `gitnest-runner` from the same release registers against the control plane, leases a trivial job, and reports its result |
| Checksum verification | Every artifact in `SHA256SUMS` matches the published file |

The smoke test uses a disposable database and a disposable data directory. It never touches an operator's instance, and it never runs against a database whose schema version is newer than the binary under test.

## 10. System-service deployment example

The conventional deployment is one host, one binary, a systemd unit per run mode, PostgreSQL on the same host or reachable by DSN, and a data directory outside the repository tree. `deploy/` holds the units and environment examples; the examples contain no secret values.

`deploy/gitnest.service`:

```ini
[Unit]
Description=GitNest (web, API, Git over HTTP, webhooks)
After=network-online.target postgresql.service
Wants=network-online.target

[Service]
Type=notify
User=gitnest
Group=gitnest
EnvironmentFile=/etc/gitnest/gitnest.env
ExecStart=/usr/local/bin/gitnest serve
Restart=on-failure
RestartSec=5
TimeoutStopSec=60
StateDirectory=gitnest
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/gitnest
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
LimitNOFILE=65536
AmbientCapabilities=
CapabilityBoundingSet=

[Install]
WantedBy=multi-user.target
```

| Deployment rule | Detail |
| --- | --- |
| One unit per mode | `gitnest.service` (serve), `gitnest-worker.service` (worker), `gitnest-ssh.service` (ssh, on a host that terminates SSH itself or beside a proxy). The runner runs under its own unit and its own account. |
| Configuration | `/etc/gitnest/gitnest.env` holds `GITNEST_PUBLIC_URL`, the database DSN, and the data directory. File mode `0640`, owned by the service account, never in the repository and never in an image layer. |
| Data directory | `/var/lib/gitnest` via `StateDirectory`, owned by the service account, on storage sized for repository growth and backed up with the database as one recovery set. |
| Reverse proxy | Terminates TLS for the public URL and forwards HTTP to the listener. It is not an authorization boundary. Public URLs are built from `GITNEST_PUBLIC_URL`, never from forwarded headers. |
| Upgrade step | Stop the worker, take the backup, run `gitnest migrate`, then upgrade and start the units in the documented order. A migration never runs from a unit's `ExecStartPre` without the operator's presence. |
| Secrets | Database credentials and the secret key come from the environment file or a root-owned file referenced by it. They never appear in a unit file, a shell history, or a log. |

The container deployment is the same shape: one process per container, the image entrypoint selecting the mode, the data directory as a volume, PostgreSQL as an external service, and readiness gating the rollout.

The environment file carries startup configuration only: database URL, bind addresses, repository storage root, data directory, public URL, log level, shutdown timeout, and the container runtime endpoint where one is used. Instance policy (registration mode, default visibility, quotas, SMTP, search backend, workspace limits) lives in the instance settings table and is changed through the operator console without a restart. A setting belongs to exactly one of the two; the split, the small set of environment overrides, and the validation rules are defined in [configuration.md](configuration.md). An upgrade never migrates a setting from one layer to the other silently.

## 11. Upgrade procedure

Per release, the documented procedure is:

1. **Read the release notes and `migration-compatibility.md`.** Identify whether the release adds migrations, whether any is classified irreversible, the expected duration and locking behaviour of each, and whether rollback is supported.
2. **Verify the artifacts.** Check the downloaded files against `SHA256SUMS` and confirm the manifest's container digest matches the image in use.
3. **Take a backup.** A backup of the coordinated recovery set (PostgreSQL plus repository storage, plus object storage where configured) is mandatory before any release that applies a schema change. An upgrade without a verified backup is not supported. The backup is verified by restoring it into a scratch instance and cloning a repository from it; a backup that has not been restored is not a backup.
4. **Run the preflight.** `gitnest migrate --status` reports the applied and expected app versions; `gitnest migrate --dry-run` lists the migrations that would be applied and exits non-zero when the database is newer than the binary. The preflight is run against a copy of the production database when the release adds data-rewriting migrations.
5. **Run the migration once, with locking.** `gitnest migrate` takes a PostgreSQL advisory lock for the migration run, so two nodes cannot migrate concurrently. The second invocation waits for the lock and then reports that the migration is already applied, or exits with a distinct "another migration is running" message after its wait budget. Each migration file runs in its own transaction and records a ledger row; a failing migration rolls back both its schema work and its ledger row.
6. **Upgrade the units in order.** Worker first, then the web nodes one at a time behind a readiness gate, then the SSH entry point. A node that fails readiness is drained and rolled back rather than left serving.
7. **Verify.** Check `/api/ready`, `GET /api/v1/meta` for the expected build and app version, clone a repository with a real Git client, and inspect the operator-visible views for failed jobs and failed webhook deliveries.
8. **Record.** Note the version, the app version before and after, the migration duration, and anything improvised. Improvisation is a documentation defect and is filed as one.

### 11.1 Rollback limits

Migrations are forward-only. There is no down migration, and editing an applied migration is forbidden.

| Situation | Supported action |
| --- | --- |
| The release applied no migration, or only additive, backward-compatible migrations | Rolling the binary back to the previous release is supported while the schema stays as it is. The previous binary must be able to serve the newer schema; the release notes state this explicitly per release. |
| The release applied a migration classified irreversible (a dropped or rewritten column, a destructive backfill, a changed key) | Rolling back the binary is not sufficient and may be unsafe. The documented recovery is to restore the pre-upgrade backup, which loses every write after the backup. |
| The release is the point of no return for a staged change (schema-first rollout) | The compatibility window is stated in the release notes; rollback is supported until the later release that removes the old shape. |
| A partially completed upgrade across nodes | Stop the not-yet-upgraded nodes, complete the migration, and bring all nodes back on one version. Running two app versions across a schema change is supported only within the stated compatibility window. |

Every release states, in one line, whether rollback is supported and which migration is the point of no return. A release that does not state this is not publishable.

## 12. Support policy for the previous release

| Item | Policy |
| --- | --- |
| Binary | The current release and the previous minor release are supported. An operator on an older release must upgrade through the documented steps, one minor release at a time, before reporting a defect. |
| Database schema | Each release documents the oldest app version it can serve (minimum supported database version) and the newest it can be upgraded from. A binary refuses to start against a database older than its minimum with a clear message naming `gitnest migrate`, and refuses to run a migration when the database is newer than the binary, rather than guessing. |
| Migration compatibility | Schema changes are additive within a compatibility window: a column or table is added, deployed, and only removed in a later release after the window closes. This is what allows the previous and the next release to run against one schema during a rolling upgrade. |
| Runner protocol | The control plane accepts the current runner protocol version and the previous one, and refuses an older runner at registration with a distinguishable error naming the minimum version. |
| Upgrade path | Upgrades from the immediately previous minor release are tested on every release. Upgrades across several minors are documented as a sequence. |
| Downgrade | Supported only through a restore of the pre-upgrade backup, or by a binary rollback within the stated compatibility window. |

## 13. Open questions

- Which platforms the support policy covers for the runner agent once the container runtime adapter is chosen; `windows/amd64` depends on that choice.
- Whether the published images are signed with a key the project publishes, or verified by digest plus checksums only. The artifact manifest is designed to carry either answer.
- Whether the reproducibility check can be extended to the container image (bit-identical image digests) or stays a binary-level guarantee with a digest-pinned base.
